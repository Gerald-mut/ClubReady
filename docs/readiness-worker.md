# Readiness worker

Phase C is local database implementation only. No scheduler, frontend changes,
Edge Function deployment or hosted access is included. Migration 006 is additive;
Phase B mappings and composite ownership/version constraints remain authoritative.

## Enqueue and generations

Activity/evidence insert, update and delete, club creation and profile changes
transactionally increment a private per-club generation and upsert one queued job.
Updates are observed even when privileged SQL makes writes unavailable to clients.
Activity UUID retry inserts with ON CONFLICT DO NOTHING produce no extra counts.
An event marks assessed snapshots stale/unknown; never-assessed fixtures stay so.

Requirement/mapping changes increment one catalogue revision per statement. They
never iterate clubs inside a trigger. Every worker call prepares at most 100
clubs needing catalogue invalidation or a UTC daily expiry sweep. Bootstrap adds
at most 100 missing club states per call, including populated upgrade databases. Initial generations start above existing
Phase B job/result generations, rather than restarting their counters.
Settings changes invalidate through the same revision. Trusted SQL may configure
private.readiness_settings.expiring_days (default 30, range 0..3650).

Catalogue fan-out is eventual: until a club is prepared, its previous snapshot
can still say current. Do not promise immediate catalogue freshness or expose a
frontend freshness contract until Phase D defines this lag. Worker invocations
must continue when no job is returned, because bounded preparation may skip
locked clubs or discover more bootstrap work in subsequent calls.

## Transaction and concurrency

process_next_job() prepares a bounded batch, locks a club state and then a due
job using FOR UPDATE SKIP LOCKED. Enqueue uses the same state-before-job order.
A shared catalogue lock prevents committed catalogue changes midway through an
evaluation; workers may share it. Curators may block until an evaluation commits.
Concurrent source/curation writes can deadlock; PostgreSQL aborts a participant.
Infrastructure should retry whole transactions on deadlock/serialization errors.

Claim, results, exact support links and completion all commit together. Running
is a real intra-transaction state, not a durable lease. Another session sees the
queued job locked until commit. A worker crash rolls back its claim and all
results; no lease timeout or abandoned-running reaper is needed. Call once per
transaction, commit promptly, and set infrastructure statement/idle transaction
timeouts. Per-club state locks prevent later generations overtaking earlier ones.
Events arriving during processing wait, then create a queued successor with a
higher generation. An evaluator refuses to overwrite a higher generation.

## Evaluation

Only explicitly mapped current requirements are evaluated. Composite foreign
keys retain the opportunity and requirement version. Missing mappings produce no
result (Phase B's result FK forbids one); they need trusted SQL curation. No text
parsing, inferred funding rules or new mappings are generated by this worker.

Unsupported, unverified and conditional requirements remain unknown/unknown.
Phase B rejects non-unknown results for every non-null condition; therefore true
and false condition evaluation is intentionally unsupported. No false eligibility
conclusion is drawn from unknown applicability. Optionality is preserved on the
requirement and does not become a denominator or applicability decision.

Documents match club and category. All matching record IDs are linked, including
expired/unknown records used to explain shortages. UTC expiry dates are inclusive:
expires_at=today is current, tomorrow's UTC date makes it expired. Counts select
status in this order:

- Enough records expiring strictly beyond today + horizon: supplied.
- Enough known current records: expiring.
- Unknown-expiry records could bridge the current count shortage: unknown.
- Enough total records, but known expired records prevent meeting the count: expired.
- Fewer total records than required: not_supplied, even for partial expired counts.

Null expiry never proves currency. This conservative choice needs product review
for categories without expiry. No opportunity-specific validity duration is
invented. Uploaded presence establishes no authenticity, legal recognition,
verification, compliance or funding entitlement.

Activities match persisted club/type and minimum count; every exact matching ID
is linked. Phase B has no activity time-window mapping, so no frequency, time
window, participation percentage or demographic inference is made. Club info
requires all explicitly mapped allowlisted fields to be non-null/nonblank. An
establishment year never establishes registration or legal recognition.

## Failures and privileges

An exception subtransaction rolls back evaluation and support writes. The outer
transaction leaves prior snapshots stale and persists attempts, SQLSTATE-only error codes and exponential delays
of 5, 10, 20 and 40 seconds before attempts 2..5. Delays are capped at 3600
seconds; processing always stops after at most five attempts, even if a trusted
writer configured a higher Phase B max_attempts. Failed jobs retain finished_at;
a subsequent source event may create new work. Events coalescing during backoff
do not reset attempts or bypass run_after. Trusted operators may inspect failed
jobs and enqueue a new generation after fixing the cause. No raw error messages,
source metadata or evidence contents are logged.

readiness_worker is NOLOGIN, granted to the database administrator postgres only.
Provision a separate trusted infrastructure login with membership in that role;
never grant it to authenticator, anon, authenticated or service_role. It can
execute only the public SECURITY DEFINER entrypoint, whose empty search_path and
qualified objects prevent path substitution. Private helpers have revoked direct
execution. Table grants/RLS remain unchanged; composite FKs enforce same-club
supports even for privileged writes. Browser and service roles cannot invoke the
worker or mutate queue/results/supports. No credentials are added to frontend.

## Validation and Phase D prerequisites

readiness_worker.sql covers deterministic evaluation, exact links, coalescing,
expiry, catalogue invalidation, generation regression, caught exceptions, backoff,
five-attempt exhaustion and denied client execution. Existing Phase B tests retain
cross-club RLS and privileged same-club integrity checks. Real concurrent psql
sessions prove SKIP LOCKED exclusion, an overlapping event with observed blocking,
and backend termination before commit followed by successful replay of that job.
These test database behavior, not an infrastructure login or scheduler service.
The final local verification runs nine root SQL suites (27 new worker assertions),
10 pgTAP assertions, three populated upgrade regressions and six real concurrent
session cases. Detailed command output is in .codex-logs/phase-c-*.log. Frontend
checks are outside this change because no application or shared frontend contract
files changed.

Phase D scheduling is documented in [readiness-scheduling.md](readiness-scheduling.md).
Its runner preserves the following unresolved evaluation/product decisions:
curate source-backed mappings, decide conditional vocabulary and
activity window schema, review null expiry, define catalogue lag/read freshness,
provision a least-privilege login, configure bounded invocations/timeouts, daily
expiry coverage, monitoring/dead-job alerts and retention. Large catalogue/club
backlogs require enough calls to drain batches; one evaluation is not capped by
requirement count. No hosted cron is enabled. Frontend integration and hosted
rollout require separate review. The historical Phase C implementation stopped here.
